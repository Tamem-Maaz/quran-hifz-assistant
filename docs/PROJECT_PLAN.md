# مشروع: المساعد بحفظ القرآن الكريم

> **حالة الوثيقة:** الإصدار 2.1 — خطة معمارية وتنفيذية
> **آخر تحديث:** 2026-08-03
> **الحالة:** معتمدة للتنفيذ. القرارات الجوهرية مثبّتة (القسم 20)

---

## 1. الرؤية والنطاق

### 1.1 الرؤية

ليس الهدف إنشاء مصحف إلكتروني أو مشغّل تلاوات أو قارئ تفسير. الهدف هو **مساعد شخصي للحفظ** يقود المستخدم خلال جلسة حفظ متكاملة، ويجيب يوميًا على سؤالين اثنين:

1. ما الذي أحفظه اليوم؟
2. **ما الذي يجب أن أراجعه اليوم مما حفظته سابقًا؟**

السؤال الثاني هو ما يحوّل التطبيق من "مسجّل تقدّم" إلى "مساعد حفظ" حقيقي، وهو محور الإضافة الأهم في هذا الإصدار من الخطة.

### 1.2 داخل النطاق

- تتبّع جلسة الحفظ اليومية بمراحلها الست.
- جدولة المراجعة الدورية (السبقي والمنزل) تلقائيًا.
- تسجيل مواضع الخطأ والمتشابهات.
- الإحصائيات وتقدير تاريخ الختم.
- النسخ الاحتياطي والاستيراد.
- العمل دون إنترنت (PWA).

### 1.3 خارج النطاق (صراحةً)

- تشغيل الصوت أو استضافة التلاوات.
- **عرض نص الآيات داخل التطبيق** — يُعرض مرجع المقطع فقط («البقرة 12 — 15»).
- عرض نص التفسير داخل التطبيق (روابط خارجية فقط).
- **تعدد المستخدمين أو متابعة المعلّم لعدة طلاب.**
- الحسابات والمزامنة السحابية والخادم الخلفي.
- التصحيح الآلي للتلاوة أو أي معالجة صوتية ذكية.

أي طلب مستقبلي يجب أن يُقاس على هذه الحدود قبل قبوله.

## 2. المستودع والاستضافة

| البند | القرار |
|---|---|
| المستودع | **عام (Public)** |
| المنصة | GitHub |
| الاستضافة | GitHub Pages |
| الفرع | `main`، النشر عبر GitHub Actions |

**ملاحظة أمنية مترتبة على كون المستودع عامًا:** الكود المصدري مرئي للجميع، وهذا مقبول ولا يمثل مشكلة لأن التطبيق **لا يحتوي على أي أسرار**: لا مفاتيح API، ولا رموز وصول، ولا نقاط نهاية خاصة. بيانات المستخدم تبقى بالكامل داخل متصفحه ولا تغادره إطلاقًا.

**قاعدة إلزامية:** لا يُضاف أي ملف `.env` أو مفتاح أو رمز إلى المستودع في أي مرحلة. إن ظهرت لاحقًا حاجة لخدمة تتطلب مفتاحًا، فذلك يستدعي إعادة نظر معمارية كاملة لا مجرد إضافة ملف.

## 3. القرارات المعمارية

| # | القرار | البديل المرفوض | التبرير |
|---|---|---|---|
| 1 | JavaScript خام + ES Modules، بلا أداة بناء | React / Vite / bundler | المتصفحات تدعم `import/export` أصلًا. النشر على Pages يصبح نسخ ملفات. تقليل تبعيات = تقليل صيانة على مدى سنوات |
| 2 | تطبيق صفحة واحدة (SPA) بتوجيه hash | صفحات HTML منفصلة | رحلة الحفظ تدفق واحد متصل. حالة واحدة في الذاكرة، بلا تكرار للهيدر، وتوجيه hash لا يسبب 404 على GitHub Pages (على عكس History API) |
| 3 | `localStorage` كمحرك تخزين أساسي خلف واجهة مجرّدة | IndexedDB مباشرة | البيانات صغيرة ومتزامنة القراءة. الواجهة المجرّدة تسمح بالانتقال إلى IndexedDB لاحقًا (عند إضافة التسجيل الصوتي) بتعديل طبقة واحدة |
| 4 | JSDoc + `checkJs` للتحقق من الأنواع | TypeScript كامل | نحصل على أمان الأنواع في المحرر و CI دون خطوة ترجمة، فيبقى ما يُنشر هو ما يُكتب |
| 5 | `schemaVersion` ودوال ترحيل منذ اليوم الأول | إضافتها عند الحاجة | لا توجد قاعدة بيانات مركزية يمكن ترحيلها لاحقًا. بيانات المستخدم موزّعة على متصفحاته، والفرصة لإصلاح ذلك بأثر رجعي **معدومة** |
| 6 | بيانات السور كملف ثابت محلي | استدعاء API خارجي | يعمل دون إنترنت، بلا حدود معدل، وبلا نقطة فشل خارجية. الحجم بضعة كيلوبايت |

### 4.1 قاعدة الفصل الصارمة

> **`src/core/` لا يستورد من `src/ui/` ولا من `src/storage/` إطلاقًا.**

كل ما في `core/` دوال خالصة: تأخذ حالة ومدخلات، وتُرجع حالة جديدة. لا `window`، لا `document`، لا `localStorage`، لا `Date.now()` مباشرة (يُمرَّر الوقت كوسيط).

الفائدة: منطق النطاق كله قابل للاختبار في Node دون متصفح، والانتقال المستقبلي إلى أي واجهة أخرى (تطبيق أصلي، امتداد متصفح) لا يمس المنطق.

اتجاه التبعية المسموح: `ui → core`، `ui → storage`، `storage → core` (للترحيل فقط).

هذا هو العقد الأساسي للتطبيق. أي تغيير عليه بعد الإطلاق يستوجب دالة ترحيل.


### 5.1 قواعد ثابتة

- **المعرّفات:** `crypto.randomUUID()` — مدعوم في المتصفحات الحديثة عبر HTTPS، و GitHub Pages يوفّر HTTPS.
- **الأوقات:** جميع الطوابع الزمنية `epoch ms` بصيغة رقم. لا سلاسل نصية للتاريخ إلا `dayKey`.
- **`dayKey`:** سلسلة `YYYY-MM-DD` محسوبة من التقويم **المحلي** للمستخدم، لا من UTC. حساب "الأيام المتتالية" يعتمد عليها حصريًا. الاعتماد على فروق الطوابع الزمنية الخام يُنتج أخطاء عند السفر أو تغيّر التوقيت الصيفي.
- **الحالة غير قابلة للتعديل في `core/`:** كل دالة تُرجع حالة جديدة. الكتابة الفعلية مسؤولية `storage/` وحدها.

### 5.2 الترحيل

```js
// storage/migrations.js
export const CURRENT_SCHEMA_VERSION = 2;

const migrations = {
  // 1 ← 2: إعدادات مرات الاستماع وطول السبق، وtargetCount لكل خطوة بسيطة
};

export function migrate(rawState) { /* تطبيق متسلسل حتى الإصدار الحالي */ }
```

قواعد الترحيل:

1. تُستدعى `migrate` عند كل إقلاع قبل أي قراءة للحالة.
2. **تصدير نسخة احتياطية تلقائية إلى مفتاح منفصل قبل تطبيق أي ترحيل.**
3. كل دالة ترحيل تحتاج اختبار وحدة بمدخل حقيقي من الإصدار السابق.
4. الترحيل للأمام فقط. لا دعم للتراجع.

## 6. رحلة الحفظ (السبق)

المراحل الست كما في الخطة الأصلية، مع تعديلات جوهرية:

| # | المرحلة | الغرض | التعديل عن الخطة الأصلية |
|---|---|---|---|
| 1 | الاستماع | تهيئة الذهن | — |
| 2 | قراءة التفسير | فهم المعنى | مصدر التفسير قابل للاختيار من الإعدادات |
| 3 | الاستماع مرة أخرى | التثبيت بعد الفهم | — |
| 4 | الحفظ بالتكرار | الترسيخ | **إضافة زر تراجع** |
| 5 | المراجعة | القراءة دون نظر | تُميَّز عن مراجعة المحفوظ القديم |
| 6 | التسميع | التحقق من الجودة | **إضافة تسجيل مواضع الخطأ** |

### 6.1 استئناف الجلسة

الجلسة تُحفظ بحالة `in_progress` بعد **كل** تفاعل، لا عند الاكتمال فقط. عند الإقلاع، إن وُجدت جلسة `in_progress` لليوم الحالي، يُعرض خيار: «استئناف» أو «بدء جلسة جديدة» (تُعلَّم القديمة `abandoned`).

هذا ليس تحسينًا اختياريًا: مستخدم الجوال سيُغلق التطبيق في منتصف المرحلة الرابعة، وفقدان 7 تكرارات من 10 مصدر إحباط كافٍ لهجر التطبيق.

### 6.2 عدّاد التكرار

```
الآيات 12 — 15
┌─────────────────────────────┐
│  ████████░░░░░░░░  4 / 10   │
└─────────────────────────────┘
      [ كررت مرة ]    [ ↶ ]
```

- زر التكرار كبير (لا يقل عن 64 بكسل ارتفاعًا).
- زر التراجع يخفض العدّاد بواحد ولا ينزل تحت الصفر.
- العدّاد داخل `aria-live="polite"` ليُعلَن للقارئ الشاشي.
- عند بلوغ الهدف: تأكيد بصري وانتقال إلى المرحلة التالية، دون قفل إمكانية الزيادة.

### 6.3 تسجيل الأخطاء أثناء التسميع

في شاشة التسميع، قائمة بأرقام آيات المقطع، وبجوار كل آية زر «أخطأت هنا» يضيف `MistakeEntry`. هذه بيانات عالية القيمة ومنخفضة الكلفة، وتغذّي لاحقًا تقرير «أكثر المواضع تعثّرًا» ومقترحات المراجعة المركّزة.

## 7. جدولة المراجعة (السبقي والمنزل)

أهم إضافة في هذا الإصدار. الخطة الأصلية عالجت مراجعة مقطع اليوم فقط، وأغفلت المحفوظ السابق — وهو ما يُفقد الحفظ فعليًا.

### 7.1 النموذج

عند اكتمال جلسة بنجاح (مرور المرحلة السادسة)، يدخل المقطع طابور المراجعة:

```js
export const REVIEW_INTERVALS_DAYS = [1, 3, 7, 15, 30, 60];
```

- **السبقي:** العناصر في الفواصل 1–3 (أول أسبوع تقريبًا).
- **المنزل:** العناصر في الفواصل 4 فما فوق.
- **متخرّج (`graduated`):** بعد اجتياز آخر فاصل، ينتقل إلى دورة ثابتة كل 30 يومًا ولا يخرج من الطابور نهائيًا — القرآن لا يُهجَر بعد إتقانه.

### 7.2 المنطق

```js
/**
 * @param {ReviewItem} item
 * @param {'passed'|'failed'} outcome
 * @param {string} todayKey
 * @returns {ReviewItem}
 */
export function applyReviewOutcome(item, outcome, todayKey) { /* دالة خالصة */ }
```

- **`passed`:** يتقدّم `intervalIndex` بواحد، ويُحسب `dueDayKey` الجديد.
- **`failed`:** يعود `intervalIndex` إلى الصفر، ويزداد `lapseCount`. المقطع الذي يتكرر إخفاقه (`lapseCount >= 3`) يُعلَّم في الواجهة كـ«يحتاج إعادة تثبيت».

### 7.3 المستحقات المتراكمة

مشكلة عملية متوقّعة: مستخدم يغيب أسبوعًا فيجد 40 مقطعًا مستحقًا، فيستسلم.

المعالجة:

- لوحة اليوم تعرض حدًا أقصى قابلًا للضبط (افتراضيًا 7 مقاطع)، مرتّبة بالأقدم استحقاقًا أولًا.
- الباقي يُعرض كعدّاد ثانوي، لا كقائمة مرعبة.
- خيار صريح «إعادة توزيع المتراكم» يوزّع المستحقات على الأيام السبعة القادمة.

**تبرير اختيار الفواصل الثابتة:** خوارزميات مثل SM-2 تتطلب تقييمًا ذاتيًا دقيقًا من المستخدم في كل مراجعة، وهي ضريبة إدراكية عالية مقابل عائد محدود هنا. الفواصل الثابتة مفهومة، متوقّعة، وقابلة للشرح للمستخدم. يمكن ترقيتها لاحقًا دون تغيير نموذج البيانات لأن `intervalIndex` و`lapseCount` محفوظان.

## 9. مصدر بيانات القرآن

### 9.1 ما هو مطلوب فعلًا

لتشغيل «اختيار السورة» و«تحديد الآيات» يكفي:

```json
[
  { "id": 1, "name": "الفاتحة", "ayahCount": 7,   "type": "meccan",  "juz": [1] },
  { "id": 2, "name": "البقرة",  "ayahCount": 286, "type": "medinan", "juz": [1,2,3] }
]
```

يُخزَّن في `src/data/surahs.json` ويُحمَّل مرة واحدة. الحجم بضعة كيلوبايت.

### 9.2 عرض نص الآيات — قرار مثبّت: خارج النطاق

**القرار (مثبّت):** التطبيق **لا يعرض نص الآيات إطلاقًا**. الاعتماد على مصادر خارجية للنص والتفسير معًا.

الأثر المعماري لهذا القرار — وهو مكسب كبير:

- لا نص قرآني في المستودع ⇒ **لا مسؤولية عن دقة الرسم العثماني**، وهي مسؤولية جسيمة يصعب ضمانها في مشروع فردي.
- لا تبعية على مصدر بيانات خارجي ولا شروط ترخيص للنص.
- حجم التطبيق يبقى ضئيلًا والعمل دون إنترنت يبقى بسيطًا.
- المستخدم يقرأ من مصحفه الورقي أو تطبيقه المفضّل، والتطبيق يتتبّع فقط. هذا **متسق تمامًا مع الرؤية** في القسم 1.1.

بناءً عليه، تعرض الواجهة **مرجع المقطع** لا محتواه: «البقرة 12 — 15».

**هذا القرار مضاف إلى النطاق المستبعد (القسم 1.3) وأي طلب لاحق بعرض النص يُعامل كتغيير نطاق جوهري لا كإضافة ميزة.**

### 9.3 روابط التفسير

قائمة مصادر معرّفة في ملف ثابت، والمستخدم يختار مصدره من الإعدادات. الرابط يُبنى من قالب:

```js
{ id: "example", label: "…", urlTemplate: "https://…/{surah}/{ayah}" }
```

كل الروابط الخارجية تُفتح بـ `target="_blank" rel="noopener noreferrer"`.

## 10. الإحصائيات والتقدم

### 10.1 مبدأ: الاشتقاق لا التخزين

الإحصائيات **تُحسب من `sessions` عند العرض** ولا تُخزَّن كعدّادات منفصلة. تخزين العدّادات يخلق مصدرين للحقيقة، وأي خلل في التزامن يُنتج أرقامًا خاطئة يستحيل تصحيحها لاحقًا.

إن ظهرت مشكلة أداء (بعد آلاف الجلسات)، الحل هو ذاكرة مؤقتة مشتقة مع مفتاح إبطال — لا تغيير مصدر الحقيقة. **لا تحسين قبل قياس فعلي.**

### 10.2 المعروض

- عدد الجلسات المكتملة · مرات الاستماع · التفسير · التكرارات · المراجعات · التسميع.
- الأيام المتتالية (الحالي والأطول) — محسوبة من `dayKey`.
- عدد الآيات المحفوظة ونسبتها من 6236.
- **تاريخ الختم المتوقع:** من المعدل الفعلي في آخر 30 يومًا، لا من الهدف المعلن. يُعرض كتقدير صريح لا كوعد.
- **أكثر 10 مواضع تعثّرًا** من `mistakes`.
- خريطة حرارية سنوية لأيام النشاط.

### 10.3 تحذير في التصميم

يجب ألا يتحوّل التتابع إلى مصدر ضغط نفسي. عند انقطاعه: رسالة محايدة داعمة، لا شماتة ولا تهويل. تُعرض «أطول تتابع» بجانب الحالي دائمًا ليبقى الإنجاز السابق محفوظًا.

## 11. النسخ الاحتياطي والاستيراد

### 11.1 هشاشة التخزين المحلي — أخطر مخاطر المنتج

`localStorage` يُمحى بـ: تنظيف بيانات المتصفح، التصفح الخفي، إعادة ضبط الجهاز، وفي بعض المتصفحات آليات تنظيف تلقائي لتخزين المواقع غير المستخدمة لفترات طويلة.

**رحلة حفظ لسنتين لا يجوز أن تضيع بنقرة واحدة.**

المعالجات:

1. تذكير بالنسخ الاحتياطي كل 30 يومًا (عبر `lastBackupAt`)، قابل للإيقاف.
2. تصدير تلقائي إلى مفتاح احتياطي قبل أي عملية خطرة (استيراد، ترحيل، إعادة ضبط).
3. رسالة واضحة في الإعدادات تشرح أين تُخزَّن البيانات وكيف تُفقد.
4. طلب `navigator.storage.persist()` عند أول جلسة مكتملة، مع التعامل مع الرفض بصمت.

### 11.2 التصدير

ملف JSON باسم `quran-memorization-backup-YYYY-MM-DD.json` يحتوي `AppState` كاملة مع `schemaVersion` و`exportedAt`.

### 11.3 الاستيراد — لا ثقة بالمدخلات

الملف المستورد **مدخل غير موثوق** حتى لو صدّره التطبيق نفسه. خط الدفاع:

1. حد أقصى للحجم (5 ميغابايت).
2. `JSON.parse` داخل `try/catch`.
3. التحقق من `schemaVersion` — أحدث من المدعوم ⇒ رفض برسالة «حدّث التطبيق أولًا».
4. تحقق بنيوي كامل: كل حقل وكل نوع وكل مدى (`surah` بين 1 و114، `toAyah >= fromAyah`، `toAyah <= ayahCount`، الطوابع الزمنية أرقام موجبة).
5. تجاهل أي حقول زائدة بدل تمريرها.
6. **فشل ذرّي:** أي خطأ ⇒ رفض الملف كاملًا. لا كتابة جزئية إطلاقًا.
7. الاستيراد **يستبدل** ولا يدمج — الدمج يخلق تعارضات وتكرارات يصعب التنبؤ بها. مع تأكيد صريح وتصدير تلقائي للحالة الحالية أولًا.

## 13. التصميم والوصولية

### 13.1 العربية و RTL

- `<html lang="ar" dir="rtl">`.
- **خصائص CSS المنطقية حصريًا:** `margin-inline-start`, `padding-inline-end`, `inset-inline`. لا `left/right`.
- الأرقام: توحيد الصيغة (عربية شرقية أو غربية) عبر التطبيق كله دون خلط.
- التواريخ عبر `Intl.DateTimeFormat('ar', …)`.
- الحذر من اتجاه الأيقونات: أسهم «التالي/السابق» تنعكس، وأيقونات مثل التشغيل لا تنعكس.

### 13.2 الخطوط

- **مستضافة ذاتيًا** في `assets/fonts/` — خصوصية أفضل، عمل دون إنترنت، ولا اعتماد على طرف ثالث.
- واجهة: **Almarai** أو **IBM Plex Sans Arabic**.
- نص قرآني (إن أُضيف لاحقًا): **أميري** أو خط مصحفي مرخّص.
- `font-display: swap` وتحميل الأوزان المستخدمة فقط.
- التحقق من ترخيص كل خط قبل تضمينه في مستودع عام.

### 13.2.1 تأكيد الأفعال المؤثّرة

- كل فعل يغيّر البيانات أو لا رجعة فيه يمرّ بنافذة تأكيد أصلية (`<dialog>`):
  إنهاء الجلسة، إنهاء الجلسة وجدولة المراجعة، نتيجة المراجعة (نجحت / لم أنجح)،
  إعادة توزيع المتراكم، إلغاء الهدف، وتصدير نسخة احتياطية.
- **عدّادات المراحل مستثناة عمدًا** (كررت مرة، استمعت، قرأت التفسير، راجعت):
  تُضغط عشرات المرات في الجلسة الواحدة، وسؤالُ تأكيدٍ عليها يُبطل الغرض من
  زرٍّ يُضغط والعين على المصحف (القسم 6.2).
- التأكيد خاصيّة في مكوّن الزرّ نفسه (`confirm`) لا سطرٌ يُكتب في كل موضع
  نداء — فلا يُنسى في موضع ويُطبَّق في آخر.
- الاستيراد وإعادة الضبط لهما تأكيدهما المزدوج القائم داخل الشاشة (القسم 11)،
  فلا تُضاف نافذة فوقه.
- نصّ التأكيد يصف الأثر الحقيقي لا الفعل: «لا تُستأنف» حين لا تُستأنف فعلًا.

### 13.3 الوصولية

- تباين ألوان لا يقل عن AA (4.5:1 للنص العادي).
- مساحة لمس لا تقل عن 44×44 بكسل.
- تنقّل كامل بلوحة المفاتيح مع مؤشر تركيز مرئي.
- `aria-live` للعدّادات والحالات المتغيرة.
- احترام `prefers-reduced-motion`.
- نوافذ الحوار أصلية (`<dialog>`) لا محاكاة: حبس التركيز وEscape سلوك المتصفح
  نفسه. التركيز الافتراضي على «رجوع» لا على التأكيد، ويعود إلى الزرّ الأصلي
  عند التراجع.
- عدم الاعتماد على اللون وحده لنقل المعنى (✅ / ⏳ / ○ مع نص بديل).

### 13.4 الأداء

- ميزانية: أقل من 200 كيلوبايت لأول تحميل (عدا الخطوط).
- تحميل كسول للخرائط الذهنية مع `width`/`height` صريحين لمنع القفز.
- تحويل صور الخرائط إلى WebP مع بديل، وتقديم أحجام متعددة عبر `srcset`.

## 14. الأمان

رغم غياب الخادم، توجد أسطح هجوم حقيقية:

| الخطر | المعالجة |
|---|---|
| **XSS المخزّن** — أخطر خطر هنا. `listenerName` و`notes` وبيانات JSON المستوردة | استخدام `textContent` حصريًا للمحتوى الديناميكي. **منع `innerHTML` نهائيًا** مع قاعدة ESLint تفرض ذلك |
| حقن عبر `location.hash` في التوجيه | قائمة سماح للمسارات المعروفة، وأي مسار غير معروف يُوجَّه إلى لوحة اليوم |
| JSON خبيث | التحقق الكامل في القسم 11.3 |
| تسريب عبر روابط خارجية | `rel="noopener noreferrer"` + عدم تمرير أي بيانات مستخدم في معاملات الرابط |
| تلوّث النموذج الأولي عبر JSON مستورد | البناء الصريح للكائنات حقلًا بحقل بدل `Object.assign` على مدخل غير موثوق |
| أسرار في مستودع عام | لا أسرار في التطبيق أصلًا (القسم 2). تفعيل GitHub Secret Scanning |

**سياسة أمان المحتوى** عبر `<meta http-equiv="Content-Security-Policy">` (لعدم توفّر رؤوس HTTP مخصصة على GitHub Pages):

```
default-src 'self';
img-src 'self' data:;
font-src 'self';
script-src 'self';
style-src 'self';
connect-src 'self';
frame-ancestors 'none';
base-uri 'self';
```

هذا يمنع تحميل أي سكربت خارجي — وهو أيضًا سبب إضافي لاستضافة الخطوط ذاتيًا.

## 15. العمل دون إنترنت (PWA)

**نُقلت من «أفكار مستقبلية» إلى نطاق أساسي.** تطبيق عادة يومية يُستخدم على الجوال، وغالبًا في أوقات وأماكن لا يتوفر فيها اتصال جيد (المسجد، السفر). العمل دون إنترنت جزء من المنتج لا إضافة عليه.

- `manifest.webmanifest` كامل: الأيقونات، `display: standalone`، `dir: rtl`، `lang: ar`.
- Service Worker باستراتيجية **cache-first للأصول** و**network-first لملف التطبيق الرئيسي**.
- **إدارة التحديث:** ترقيم إصدار الذاكرة المؤقتة وحذف القديمة عند `activate`، مع إشعار داخل التطبيق: «يتوفر تحديث — إعادة التحميل». بدون ذلك يعلق المستخدمون على نسخة قديمة إلى الأبد، وهي أشهر مشكلات PWA على GitHub Pages.
- اختبار صريح لمسار الترقية: نسخة قديمة مثبّتة ← نشر جديد ← التحقق من ظهور الإشعار وتفعيله.

## 16. الاختبارات

| الطبقة | الأداة | التغطية المطلوبة |
|---|---|---|
| `core/` | Vitest (Node، بلا متصفح) | ≥ 90% — دوال خالصة، لا عذر |
| `storage/` | Vitest + بديل `localStorage` | الترحيل والتحقق ومسارات الفشل |
| التدفقات الحرجة | Playwright | رحلة حفظ كاملة، استئناف، دورة تصدير/استيراد |

### 16.1 حالات حافة إلزامية

- تجاوز منتصف الليل أثناء جلسة مفتوحة.
- تغيّر المنطقة الزمنية بين جلستين (سفر).
- التوقيت الصيفي (يوم من 23 و25 ساعة).
- انقطاع التتابع ثم استئنافه.
- `localStorage` ممتلئ (`QuotaExceededError`) — يجب ألا يُسقط التطبيق، بل يعرض رسالة ويقترح التصدير.
- جلسات متعددة في اليوم الواحد.
- مقطع من آية واحدة، ومقطع يغطي سورة كاملة.
- استيراد ملف تالف / بإصدار مخطط أحدث / فارغ.
- طابور مراجعة بـ 200 عنصر مستحق.
- ضغط سريع متكرر على زر التكرار.

### 16.2 مبدأ

اختبار السلوك لا التنفيذ. الاختبارات التي تتحقق من بنية DOM الداخلية هشّة وستُحذف عند أول إعادة هيكلة، فتفقد قيمتها.

## 17. CI/CD

**`ci.yml`** — عند كل دفع وطلب دمج:

1. `npm ci`
2. ESLint (مع قاعدة منع `innerHTML`)
3. `tsc --noEmit --checkJs` للتحقق من أنواع JSDoc
4. Vitest مع تقرير التغطية
5. Playwright على التدفقات الحرجة

**`deploy.yml`** — عند الدمج في `main` ونجاح CI: النشر على GitHub Pages.

**التراجع:** كل نشر مرتبط بـ commit، والرجوع = إعادة نشر commit سابق. مع Service Worker يجب التحقق من أن التراجع لا يترك المستخدمين على نسخة معطوبة مخزّنة.

## 18. مراحل التنفيذ

أُعيد ترتيبها لأن الترتيب الأصلي كان يضع النسخ الاحتياطي في المرحلة السادسة والاختبارات في السابعة — أي أن أول مستخدم حقيقي كان سيجمع بيانات أسابيع دون أي وسيلة لحمايتها.

| المرحلة | المخرجات | معيار الاكتمال |
|---|---|---|
| **1. الأساس** | نموذج البيانات، `storage/`، الترحيل، التحقق، إعداد CI، اختبارات وحدة | تغطية ≥ 90% لـ `core` و`storage`، وأنابيب CI خضراء |
| **2. الرحلة الأساسية** | `surahs.json`، المراحل الست، الاستئناف، التوجيه، هيكل الواجهة | إتمام جلسة كاملة والاستئناف بعد إغلاق المتصفح |
| **3. حماية البيانات** | التصدير، الاستيراد المتحقَّق، إعادة الضبط، تذكير النسخ | دورة تصدير→ضبط→استيراد تعيد الحالة بالضبط |
| **4. المساعد الحقيقي** | جدولة المراجعة، لوحة اليوم، السبقي/المنزل، سجل الأخطاء | مقطع محفوظ يظهر مستحقًا بعد يوم واحد |
| **5. التحفيز** | الإحصائيات، التتابع، الهدف، الختم المتوقع، الخرائط الذهنية | — |
| **6. دون إنترنت** | PWA، Service Worker، إدارة التحديث | التطبيق يعمل كاملًا في وضع الطيران |
| **7. الصقل** | تدقيق الوصولية، ميزانية الأداء، Playwright، التوثيق | لا مخالفات AA، والميزانية محقّقة |

المرحلة 4 هي التي تُحقق الرؤية. كل ما قبلها بنية تحتية، وكل ما بعدها تحسين.

القرارات التالية **مؤكَّدة ومغلقة** بتاريخ 2026-08-03، ونموذج البيانات في القسم 5 مبني عليها. إعادة فتح أيٍّ منها بعد المرحلة 1 تتطلب دالة ترحيل واختبارها.

| # | القرار | التنفيذ | كلفة إعادة الفتح لاحقًا |
|---|---|---|---|
| 1 | **المقطع لا يمتد عبر سورتين** | `Portion` يحمل `surah` واحدًا. التحقق: `1 ≤ surah ≤ 114`، `fromAyah ≤ toAyah ≤ ayahCount[surah]` | متوسطة — ترحيل `Portion` وكل ما يشتق منه |

| 3 | **مستخدم واحد** | `AppState` بلا طبقة `users`. لا معرّف طالب في أي كيان | **عالية جدًا** — إعادة كتابة جذر النموذج وكل دوال `core/` |
| 4 | **نص الآيات خارجي بالكامل** | الواجهة تعرض المرجع لا المحتوى. راجع 9.2 | متوسطة + التزامات ترخيص ودقة رسم |
| 5 | جلسات متعددة في اليوم مسموحة | التتابع يُحسب بـ`dayKey` الفريد لا بعدد الجلسات | منخفضة |

### 20.1 المكاسب المعمارية المترتبة

القراران 3 و4 يبسّطان المشروع جوهريًا:

- **مستخدم واحد** ⇒ `AppState` كائن واحد مسطّح، بلا فهرسة أو عزل بيانات أو صلاحيات. كل دوال `core/` تأخذ الحالة كاملة وتُرجعها. لا تعقيد استعلامات إطلاقًا.
- **بلا نص قرآني** ⇒ حزمة التطبيق تحت 200 كيلوبايت بسهولة، والعمل دون إنترنت يصبح تخزينًا لبضعة ملفات، ولا مسؤولية عن دقة الرسم.

النتيجة: التقدير الواقعي أن `core/` كله لن يتجاوز بضع مئات من الأسطر — وهذا بالضبط ما يجعل تغطية اختبار 90% هدفًا معقولًا لا طموحًا.

### 20.2 مسائل مؤجَّلة (لا تحجب البدء)

| المسألة | الافتراض العامل | متى تُحسم |
|---|---|---|
| هل تُحتسب المراجعة وحدها في التتابع، أم يلزم سبق جديد؟ | **نعم تُحتسب** — يوم مراجعة كامل يوم نشاط | قبل المرحلة 5 |
| هل تُحفظ الجلسة `abandoned` أم تُحذف؟ | تُحفظ (تُفيد في تشخيص التعثر) | قبل المرحلة 5 |
| ترتيب المراجعات المستحقة عند تجاوز الحد اليومي | الأقدم استحقاقًا أولًا، ثم الأعلى `lapseCount` | قبل المرحلة 4 |

هذه الثلاث تقع كلها داخل `core/` ولا تمس نموذج البيانات، فكلفة تأجيلها منخفضة.

## 21. أفكار مستقبلية

مرتّبة بنسبة القيمة إلى الكلفة، خارج النطاق الحالي:

1. **تقرير المتشابهات** — تجميع مواضع الخطأ لاقتراح مقارنات مركّزة.
2. **التسجيل الصوتي الذاتي** — عبر `MediaRecorder` لمن لا يجد مسمِّعًا. يتطلب الانتقال إلى IndexedDB (وهو ما تسمح به الواجهة المجرّدة في القسم 3).
3. **التذكيرات** — عبر Notification API. محدودة على iOS، تحتاج تحققًا قبل الوعد بها.
4. **خطط حفظ متعددة** — «حفظ» و«تثبيت قديم» بالتوازي.
5. **الإنجازات** — بحذر شديد: التحفيز الخارجي قد يُفسد النية في هذا السياق تحديدًا.
6. **مزامنة اختيارية** — GitHub Gist أو ما شابه. تُدخل حسابات ومفاتيح وأسرار، وتناقض القسم 2 — تحتاج مراجعة معمارية كاملة لا إضافة ميزة.
7. **تعدد اللغات** — بنية النصوص قابلة للفصل من الآن دون كلفة تُذكر.
